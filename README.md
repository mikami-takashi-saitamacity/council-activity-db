さいたま市議会議員・三神たかし（三神尊志、見沼区選出）が、2007年の初当選以来、議会で行った質問・予算提案の記録を構造化したデータです。

## なぜ公開するのか

議事録は市議会のサイトで公開されていますが、「この議員が何を提案し、行政がどう答え、その後どうなったか」を市民が追うことは難しいのが実情です。

このデータは、議員の実績を宣伝するためのものではなく、**議員活動そのものを後から検証できる公開記録**として作りました。実現した提案だけでなく、「検討・対応予定」のまま止まっているもの、「提案のみ」で終わったものも、すべて含めています。

同じ構造で他の議員が公開すれば、有権者が党派を越えて議員活動を比較できるようになります。データ構造ごと自由に使ってください。

## データの作り方と、正直に書いておくべきこと

### 出典

さいたま市議会の公開議事録（本会議・委員会）および予算関連資料。

### 抽出・構造化

公開議事録から質問・提案を1件ずつ抽出し、生成AI（ChatGPT・Claude）を使って要約・分類しました。取得にはブラウザ操作を自動化するツール（Playwright）と手作業を併用しています。現在は自動取得を止め、議員本人の発言データを機械可読な形で提供してもらう正式なルートについて、議会局に打診しています。

なお、本リポジトリの運営(データの検証、Issue への返答、ドキュメントの作成等)にも AI(Claude)の支援を受けていますが、判断と文責はすべて三神本人にあります。

### 対応状況（result_level）の判定

**判定は三神本人が行っています。** 第三者による判定ではないことを前提に、判断の根拠は各件の要約（`answer_summary`）と、可能な限り整備している議事録原文へのリンクで確認してください。

6区分は、行政答弁の言い回しの段階（実施 ＞ 対応予定 ＞ 検討 ＞ 研究 ＞ 応答なし）にほぼ対応しています。「研究する」は「検討する」より手前、という議会での慣用を前提にしています。「適正確認」だけは進み具合ではなく質問の目的による区分です。

| 区分 | 使うとき | 答弁・回答の典型 |
|---|---|---|
| 実施済 | 提案した内容が実現した。答弁の時点で実施が決まっていたものと、答弁後に実現を確認したもの（`follow_up` に記載）の両方を含む | 「〜を実施する」「〜年度から開始」、後日の事業化・条例化 |
| 改善・対応予定 | 答弁で具体的な対応（内容・時期・事業）が示されたが、実現はまだ確認できていない | 「〜に取り組む」「〜年度中に方針を決定」「補正予算に計上」 |
| 検討を引き出した | 答弁が「検討する」と明言したが、内容や時期は示されていない。検討会議・委員会の設置を含む | 「検討する」「〜を含めて検討」 |
| 研究段階 | 答弁が「研究する」「他自治体の事例を参考に」にとどまる。検討より手前の段階 | 「研究する」「動向を注視」「事例を参考に」 |
| 提案のみ | 答弁が提案に直接応じていない、既存の取組の継続を述べるだけ、または実施しないと回答 | 「引き続き〜に努める」「現時点で予定はない」、明言なし |
| 適正確認 | 質問の目的が改善の要求ではなく、行政の判断・手続き・条例の文言が適正かを確かめることにあり、答弁でそれが確認できた。求めた変更がない点で「提案のみ」と、何かが変わったわけではない点で「実施済」と異なる。主に委員会の議案審査 | 入札方式の確認、条例改正の趣旨の確認、審査基準の根拠の確認 |

判定は原則として答弁の時点で行い、その後の進展は `follow_up` に記録します。答弁後に実現が確認できた件は「実施済」に判定し直しています。したがって同じ答弁内容でも、確認時期によって判定が異なる場合があります。

会派の予算提案（324件）は市の回答文書が定型的なため、「改善・対応予定」「研究段階」に集中しています。「適正確認」は予算提案ではほとんど使っていません。

### follow_up_evidence（提案後の進展を裏付ける根拠）

`follow_up` が自由記述であるのに対し、`follow_up_evidence` は根拠を構造化して記録します。分類を書くのではなく、確認できた事実だけを書きます。

| 要素 | 内容 |
|---|---|
| `council_ref` | 議会で実施状況を確認した質問の会議録URL |
| `evidence_title` / `evidence_url` | 実施を示す行政資料の名称とURL |
| `verified_date` | 行政資料の存在を最後に確認した日（`evidence_url` 記入時は必須） |

記入状況から、次のように表示が導かれます。

| council_ref | evidence_url | 表示 |
|---|---|---|
| あり | あり | 議会・行政資料で確認 |
| あり | なし | 議会で確認 |
| なし | あり | 行政資料で確認 |
| なし | なし | （表示なし。`follow_up` の自由記述のみ） |

議会で確認した案件と、行政資料でのみ確認した案件を区別して見せるのは、両者の信頼度が異なるためです。

### 収録方針

全期間(2007年〜)の質問・提案の網羅を目指していますが、現在も精査中です。年ごとの件数には差がありますが、これは活動量の変動だけでなく、役職による発言の制約(市民生活委員長 2013.6〜2015.6/決算特別委員長 2018.6〜2019.4/副議長 2022.12〜2023.4/予算委員長 2023.5〜2024.6 の期間は、質問・質疑する側に立たない場面が多くなります)が影響しています。また、古い年代については AI 処理での取りこぼしの可能性もあり、確認を続けています。

### 既知の課題

公開データのみに基づく外部からの検証([Issue #1](https://github.com/mikami-takashi-saitamacity/council-activity-db/issues/1))で、構造上の問題の指摘を受けました。指摘はすべて事実と確認済みで、対応方針は Issue 上で公開しています。

- **予算提案324件の `date` に、年度を表す仮の日付(各年1月1日)が入っています。** このまま時系列の分析には使えません。`year` 項目の新設を含むスキーマ改訂で対応します
- **`meeting_type` がスキーマの定義と一致していない件が316件あります。** 予算提案の大半が「本会議」となっていますが、実際に本会議の議事録に基づく発言は88件です。会議種別での集計は現時点では正確ではありません
- **`source_url`(71件)に、同一の URL が日付の異なる件に貼られているなどの不整合があります。** 件数を増やすより先に、既存分の貼り直しを優先します

従来からの課題:

- 対応状況の判定精度にばらつきがあります
- 質問・答弁の要約が粗く、一部で整合が取れていない箇所があります
- 議事録原文へのリンク(`source_url`)は666件中71件、答弁後の状況(`follow_up`)は111件にとどまっています

誤りに気づいた方は、Issue でお知らせいただけると助かります。

## 使い方の例

- **市民・記者**：JSONを生成AI（ChatGPT、Claude、Gemini等）に読み込ませて、「医療についてどんな提案をしたか」「実現していない提案は何か」と質問する
- **研究者**：政策分野・年・対応状況で集計し、議員活動の傾向を分析する
- **他の議員**：schema.json の構造をそのまま使って、自分の議会活動を同じ形式で公開する（詳しくは下記）

---

## 他の議員の方へ

このデータ構造は、そのまま使っていただいて構いません。ただ、私が作った形が最適だとは思っていません。「この項目が足りない」「判定基準はこうすべき」という改善提案をいただければ、一人で作ったものより、より良い共通の形にしていけると思います。

すでに複数の議員から関心を寄せていただいており、AIに慣れていない方でも導入しやすい方法を、賛同してくださる技術者の方と検討しています。

- 改善提案・不具合の報告：このリポジトリの [Issues](https://github.com/mikami-takashi-saitamacity/council-activity-db/issues) から
- 導入のご相談・GitHubに不慣れな方：https://mikami-takashi.net/#contact から

同じ構造で公開する議員が増えれば、有権者は党派や知名度ではなく「何を提案し、その後どうなったか」で議員を比べられるようになります。

定例会（年4回）終了後に随時追加します。件数・内訳は本READMEの記載時点のものです。更新履歴はこのリポジトリのコミット履歴で確認できます。

## 今後

- スキーマ改訂:`id` の付与、`year` の新設、`meeting_type` の修正を、再生成スクリプトの整備後、次の定例会分の追加と同時に一括で実施します(データの実体が複数箇所にあるため、個別修正は行いません)
- `source_url` の総点検・貼り直し(既存71件)。予算提案は「正本文書の URL+文書内の位置」の2段構成とし、正本 PDF の複製をリポジトリに保管してハッシュ値を記録します(議事録は転載規約により複製を持たず外部リンクのみ。この非対称は仕様として明記します)
- 「質問・提案 → 当時の答弁 → その後の答弁・予算・事業 → 現在の状態」まで追跡できる構造への拡張
- 他の議員が同じ構造で公開するための手順書
